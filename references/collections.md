# Growing collections and limits

Apply this when the target shows a list that grows with user input, such as selected people, tags, chips, avatars, recipients, or attachments, or a limit the user can reach, such as a size quota, seat count, or character budget. Collapsing a list or changing how a limit is shown is presentation, not new product behavior: every item and every existing action must stay reachable. Disclose each new label you write, such as "+12 more".

- Cap an inline list of chips or tokens to a fixed few (three is a good default) or to what fits one row, then end it with one control that names the rest, such as "+12 more". Never let chips wrap into a scrolling box inside a header. The control opens the full list in the project's dialog or popover (`aria-haspopup="dialog"`), and focus returns to it on close.
- In the full list, keep each row's existing action, such as remove, with an accessible name that includes the item ("Remove Jane Doe"). Add search once the list is long enough to scan (about eight items). Offer a bulk action such as "Remove all" only when the product already has it, for example a clear-selection handler. Close the list when its last item is removed.
- Show a group of people as an avatar stack: up to three overlapping avatars, then a "+N" bubble. Put the bubble behind the avatars (lower `z-index`) so faces stay on top, and separate overlaps with a ring in the surface color. Hide the stack from assistive technology when nearby text already states the count.
- Show a limit as a small meter, not only as text: the project's progress primitive with `role="progressbar"`, an accessible name, and `aria-valuetext` in the user's units ("3.8 MB of 10 MB"). Keep the value as visible text beside the bar, because color alone carries no meaning. Use the project's status tokens: success below about 70 %, warning up to full, danger when full.
- When the limit is reached, remove the input that adds more and put a sentence in its place that says how to free room ("10 MB limit reached. Remove a file to add another."). A grayed-out control that cannot work is noise. Restore the input as soon as there is room.
- When input is rejected (wrong type, over the limit), keep the reason inline next to the control, where it stays until the next attempt, and also raise one toast through the project's notifier, because the control may be scrolled out of view. Group several rejections into one toast that counts them and lists each reason.
- Animate only what the user changed, briefly (150 to 300 ms, ease-out): an added chip or avatar fades and zooms in from about 95 %, a changing count rolls, and a meter animates its width and color. Turn every one off under `prefers-reduced-motion`. Animate counts with the project's number component when one exists.

Done when: no inline list grows without bound, every hidden item and its actions are one control away, a reachable limit is shown as a meter with visible text, a full limit removes its input and says how to free room, and rejections are both inline and announced.
